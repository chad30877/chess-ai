# Issue tracker：本機工作票

本專案的規格與工作票以 `.scratch/<功能名稱>/` 的 Markdown 為狀態來源，不發布 GitHub Issues。每批以索引連結規格與工作票，一張票存一個檔案，記錄狀態、驗收條件及阻擋關係。

## 切分與定位

- 新規格放在該批的 `spec.md`，工作票放在 `issues/`；索引列出各票的狀態與阻擋。以本機編號、標題或檔名定位，不以歷史 GitHub 編號判定目前狀態。
- 切票時，一個勾選項只放一個可判定的成果並寫明驗證方式；功能驗收與文件／提交分開。只有必要且只能由使用者完成的驗收才要求使用者參與，人工重現方式不等於已執行。
- 開始實作或審查前讀取本機規格、最新工作票、索引及阻擋關係；阻擋票尚未完成時不宣稱已解除依賴。舊 GitHub 工作票與留言存於 `.scratch/github-issue-archive/`，僅供追溯。

## 驗收與結案

1. `/implement <工作票>` 包含該票的必要實作、驗證、審查、本機同步及結案；不需在完成後再次詢問是否結案。
2. 逐條依證據判斷驗收，分清自動測試、Agent 實際操作及使用者確認；只提供操作步驟不等於已執行。一般 UI 流程可用實際應用程式事件整合測試及必要畫面檢查。資料選擇、教師預算及正式長實驗是交付後可操作流程，不自動成為實作前的等待條件。
3. 更新本機票的勾選、證據、限制與狀態，並同步批次索引及開發計畫。必要驗收未完成時標示「待驗收」，保留未勾選項，不宣稱完成；不能默默降低已核准的驗收要求。
4. 提交程式與文件，讀回確認本機票、索引及計畫一致；不連帶結案其他票。最終回覆列出狀態、提交、驗證、未完成項及簡單人工測試方式。

## 技能操作對照

- 「發布到 issue tracker」：保存至該批 `.scratch/` 的規格或工作票，不建立 GitHub issue。
- 「取得相關 ticket」：讀取該批本機索引、規格及工作票。
- GitHub 發布索引和檢查工具是歷史資料，不用於本機工作票的定位或結案。
