# 網頁介面 訪談紀錄

2026-11-04 訪談。候選排名的決策另見 [candidate-ranking](candidate-ranking.md)。

## 第 1 輪：範圍與切分

- 本輪把整個介面改成網頁，pygame 退場，前端採用 Angular：使用者預期最終會全面改用網頁，不想分兩次做。被推翻的方案：先只把比較候選相關頁做成網頁試點（範圍 C）。
- 先做 `web-ui`，再做 `candidate-ranking`，兩者是不同功能，各自開分支、各自結案：光是搬家的工作量就和整套介面相當，混在一起難以驗收。
- 比較候選這一區只搬新流程需要的部分：候選清單、對 stable 比較、比較紀錄。快速篩選和雙基準完整比較不搬，依據見 candidate-ranking 第 4 輪。
- 成本依據：現有介面約 6,600 行，其中學習實驗約 3,100 行。engine 裡的各種執行物件已經可以直接包成 API；工作互斥、返回頁和背景工作的上下文只存在介面物件裡，要重新整理成由伺服器管理的狀態。

## 第 2 輪：架構

- 用 `python -m apps.web` 啟動：由 FastAPI 提供 API 和 Angular 編譯後的檔案，並自動開啟瀏覽器。開發時用 `ng serve`，再把 API 請求代理到 FastAPI。平常使用不需要 Node。
- 前端編譯產物不進版控。找不到編譯產物時，啟動畫面提示先建置：避免每次改前端都產生大量差異。
- 操作走 REST，即時狀態用 SSE 推送：資料只需要從伺服器推到瀏覽器。被推翻的方案：WebSocket（不需要雙向）、前端輪詢。
- 棋盤自己寫成 SVG 元件，合法走法和升變交給後端的 python-chess 判斷：chessground 採 GPL 授權，會牽連整個專案的授權。
- 選檔改用網頁對話框：由伺服器列出本機的資料夾和檔案，預設從專案目錄開始，可以直接貼上路徑，也可以依用途過濾。被推翻的方案：沿用 tkinter 原生選檔，因為它的外觀無法調整，和網頁介面不一致。
- 工作由伺服器負責：關掉瀏覽器時工作照常繼續；關閉伺服器時才停止並保存，之後可以手動續跑。整台電腦同一時間只跑一個重度工作，用跨程序有效的鎖控制。
- 伺服器只接受 127.0.0.1 的連線，不做登入：選檔對話框能看到本機所有檔案。
- 目錄配置：Angular 放 `web/`；`api/` 只負責轉接 `engine/`，不寫運算邏輯；啟動入口是 `apps/web.py`；設計規範寫在 `docs/設計系統.md`。
- 新增 `requirements.txt`，列出現有依賴，再加上 fastapi 和 uvicorn，全部安裝在 `.venv`：目前只在 README 寫了一行安裝指令。
- 測試分三層：後端 API 用 pytest，介面測試中的流程斷言改寫成 API 測試；前端用 Angular 單元測試；另外寫少量 Playwright 端到端測試，瀏覽器安裝在專案內並列入 `.gitignore`。依賴 pygame 的測試隨 pygame 一起移除，engine 的測試這輪不動。檢討測試是否必要另列 future-ideas。

## 第 3 輪：設計與交付

- 元件用 Angular Material。外觀依 design-taste-frontend 工作畫面模式挑選的方向自訂主題，再用 Design 外掛的 design-system 整理成規範；每一頁都要經過 taste 截圖修正和 design-critique 審查。被推翻的方案：PrimeNG（風格較雜）、完全手寫 CSS。frontend-design 和 taste 功能重疊，所以不採用。
- 深淺色跟隨系統設定，使用緊湊密度：介面以表格和清單為主。
- 元件規則：
  - 輸入、選項、清單和動作分別使用不同元件，只有動作做成按鈕。
  - 每個區塊最多一個主要按鈕。
  - 不能使用的動作要說明原因。
  - 錯誤、警告、成功各有顏色和圖示。
  - 優先顯示名稱，識別碼收在詳細資訊裡，可以複製。
  - 文字靠左對齊，數字靠右對齊。

  依據：截圖審查發現，輸入、選項、清單列和動作全都畫成同一種按鈕，錯誤和統計數字也混在一起。
- 側欄分四區：對戰、對局紀錄、批次對戰、學習實驗。每一頁都有自己的網址，「返回」就是瀏覽器的上一頁；執行中的工作固定顯示在頂端工作列。這樣可以取代 pygame 的位置路徑和返回頁狀態。
- 學習實驗改成以研究頁為中心。一份資料對應一個研究頁，頁面依序排出資料、教師先導、教師標記、權重學習、候選比較五張步驟卡；每張卡只顯示狀態、兩三個關鍵數字和一個主要動作，詳細內容預設收起。資料、教師評分、候選、比較紀錄則改成可搜尋、可排序的清單頁。依據：現在每一頁都把選來源、設定、執行、看結果、看歷史混在一起，線性的流程又被拆成平行的分頁，使用者得自己記住做到哪一步。
- 流程分岔時，教師標記卡和權重學習卡用「目前使用」切換版本，下游的卡片跟著更新；選擇記在 `data/learning-ui.json`。被推翻的方案：每條路徑各建一個研究，這會讓同一份資料重複出現。
- 首頁放四塊：進行中的工作、可以續跑的工作、最近的研究和對局紀錄（各 5 筆）、新對局／新批次／新研究三個入口。未完成工作的掃描改在伺服器啟動時於背景執行並快取：現在一進學習實驗，就要排隊等約 3 秒。
- 功能維持不變、不增不減，版面依網頁慣例重新設計。三頁的難用之處，先用截圖審查清單和使用者確認；到第 5 階段，再做可以點選的原型確認。
- 分六個階段交付：
  1. 後端骨架、外殼、工作列、全機工作鎖、選檔對話框、設計規範與主題
  2. 對局紀錄與回放
  3. 評分草稿編輯與真人對 AI
  4. 批次對戰
  5. 學習實驗
  6. 移除 pygame，補端到端測試

  搬家期間 pygame 照常可用，兩邊靠工作鎖互相避讓。先從唯讀頁面開始，可以在影響最小的地方驗證技術選擇。
- 第 1 階段由 Claude 實作，定下 API、SSE、工作鎖、Angular 結構和主題的寫法；第 2～6 階段用 codex-handoff 交給 Codex，Claude 負責審查。每個階段的驗收包括：API 測試、1280 和 900 兩種寬度的截圖、design-critique，以及使用者親自操作。
