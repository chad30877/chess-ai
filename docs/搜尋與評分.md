## 用途

負責 AI 每一步如何選：玩家策略決定選步方式，評分器判斷局面好壞，搜尋器往後探索多手。完整對局的執行與統計交給 [自動對戰](自動對戰.md)。

## 介面與評分視角

- `engine/game.py`：包裝建立棋盤、取得合法走法、檢查走法後落子、判斷結束。主要規則來自 `chess.Board`。
- `engine/interfaces.py`：定義 `Player.choose_move(board)` 與 `Evaluator.evaluate(board)` 兩個協定，方便替換策略與評分器。

**評分固定使用白方視角：正分對白方有利，負分對黑方有利。** 不會因輪到黑方而自動翻轉符號。白方選高分、黑方選低分。

## 玩家策略

`engine/players.py` 提供：

| 玩家 | 選步方式 | 目前用途 |
| --- | --- | --- |
| `RandomPlayer` | 從合法走法隨機選一手 | 資料產生、UI 與對戰 CLI 的基準對手 |
| `GreedyPlayer` | 每個合法走法各試下一手，選評分最好的局面；同分隨機選 | 資料產生、UI Demo 與現有對戰 CLI |
| `AlphaBetaPlayer` | 呼叫注入的 `Searcher`，使用回傳的 `best_move` | 多步搜尋的玩家介面；可用 `from_evaluator()` 快速建立 |

現在 `GreedyPlayer()` 的預設評分是 `HandcraftedEvaluator`（子力＋位置表）。但 `scripts/engine_match.py` 的 `material` 選項明確使用 `MaterialEvaluator`，只算子力。兩者目前不是相同設定。

## 評分器

- `engine/evaluator.py`：`MaterialEvaluator` 計算白方子力減黑方子力；預設兵 1、馬 3、象 3、車 5、后 9。`HandcraftedEvaluator` 再加上 PST 位置分數。`evaluate_material()` 與 `evaluate()` 是函式形式的入口。
- `engine/pst.py`：為六種棋子各定義一張 8×8 棋子位置表。例如馬在中央的分數較高。黑方以同檔、上下鏡射的白方表計分，再算白方總分減黑方總分。目前只有一組表，沒有開局／殘局分階段切換。
P1 已移除舊 ML 評分器與相容別名；子力、PST 與搜尋行為保持原樣。後續方向見 [評分調整與實驗](評分調整與實驗.md)。

## 搜尋流程與目前限制

- `engine/search/types.py`：`SearchLimits` 保存深度與預留時間限制；`SearchResult` 回傳走法、白方視角分數、到達深度、節點數與剪枝次數；`Searcher` 定義搜尋介面。
- `engine/search/alphabeta.py`：實作深度限制的 Minimax 與 Alpha-Beta 剪枝。白方最大化、黑方最小化。到達深度或終局才計分。
- 將死使用約正負一百萬的分數，依距離微調，以偏好較快獲勝、較晚被將死；已處理的和棋終局回傳 0。
- `max_depth` 以 **ply（半回合：任一方走一手）** 計算。深度 2 表示看自己一手及對手一手。

目前的限制：

- `time_ms` 只驗證數值並保存，搜尋沒有計時或提前停止。
- 尚無迭代加深、走法排序、置換表或靜態搜尋（quiescence search）。
- 每個子節點使用 `board.copy(stack=False)`，不保留前面的走法歷史。因此，雖有五次重複局面終局判斷，搜尋分支中的歷史重複仍不完整。
- `GreedyPlayer` 直接呼叫評分器，沒有經過搜尋器的統一終局計分；目前評分器約定針對非終局，這個接點仍需整理。

## 使用方式

在專案根目錄、已安裝依賴的 Python 環境中執行以下程式。環境設定見 [README](../README.md#環境設定)。

對戰 CLI 目前只有 `material` 與 `random`，沒有 `alphabeta`。可在 Python 中直接使用：

```python
import chess
from engine.evaluator import HandcraftedEvaluator
from engine.search import AlphaBetaSearcher, SearchLimits

board = chess.Board()
searcher = AlphaBetaSearcher(
    evaluator=HandcraftedEvaluator(),
    limits=SearchLimits(max_depth=3),
)
result = searcher.search(board)
print(result.best_move, result.score, result.nodes_searched)
```

## 與共用棋規的關係

**本次已完成自動對戰與回放的必要共用入口；搜尋整合仍待後續處理。** `engine/game.py` 持續以 `chess.Board` 提供合法走法、落子與終局結果。新增批次可保存申請和棋政策；目前生成器仍僅 Random／Greedy，不使用 Alpha-Beta。UI 也僅提供 Random／Greedy；真人模式由背景執行緒選步、主執行緒落子，批次模式在背景 worker 執行整盤並保存，介面只讀進度；Alpha-Beta 尚未接入 UI。本次批次與 UI 整理未改動既有搜尋演算法、評分權重及搜尋實作。

棋規核心判定是否終局及原因，搜尋層再把結果映射為白方視角分數（例如將死分數與距離加減）。搜尋深度與時間預算屬於搜尋限制，不是整盤棋的勝負規則。搜尋中的 `copy(stack=False)` 歷史遺失問題仍需另外修正，不能因入口統一就宣稱重複局面判定已完整。

整體分工見 [README](../README.md#共用棋規與資料分類規劃)。

## 獨立權重與設定規劃

狀態：待做，對應 [P4](開發計畫.md#p4-建立可調評分設定)。目前只有子力權重可注入，PST 固定寫在表中，兩者直接相加。

第一版抽出特徵計算、設定與分項輸出：保持白方視角及兵值 1；預設權重重現既有分數；先固定子力初值與 PST 表內容，再提供 PST 倍率、項目開關及設定版本。現有自訂子力能力保留，不趁本階段改預設棋力。

每項規格包含原始值、單位、正負方向、適用階段、權重與重複計分風險。分項輸出保存原始值、權重、貢獻與總分；開關／零權重不應殘留貢獻。實作前決定無效值處理與設定相容方式，測試覆蓋預設等價、各項效果、加總與設定往返。

`strategy_config()` 必須記錄實際注入的設定，不能從另建的預設 GreedyPlayer 推測。設定快照由對戰層保存，評分器不負責寫檔。調整流程見 [實驗文件](評分調整與實驗.md#手動比較流程規劃)。

## 評分擴充規劃

狀態：全部待做，依 [P6](開發計畫.md#p6-分批擴充評分與搜尋) 每次選一組，不同時調搜尋。

| 子項 | 範圍 | 最小驗收 |
| --- | --- | --- |
| E1 分階段評分 | 中局／殘局分數按剩餘子力平滑混合；PST 及權重變更明確記錄 | 階段邊界、鏡射對稱與混合公式正確，避免突然跳分 |
| E2 兵形 | 孤兵、疊兵、通路兵；推進程度另定清楚 | 人工局面符合定義，每項獨立關閉／調權重 |
| E3 活動力 | 各棋種活動空間，明確區分攻擊格與合法走法 | 不只計算輪到的一方，受釘住等語意寫清楚 |
| E4 國王安全 | 兵盾、受攻擊區域／開放線，依階段處理 | 安全特徵與殘局王活動不衝突，不以易位權推測是否曾易位 |
| E5 棋子協調 | 雙象、車的開放／半開放線等，必要時再拆子項 | 相應局面與特徵方向可驗證；記錄與其他項目的重複貢獻 |

每組包含明確定義、初始權重／開關、分項輸出、單元測試與比較計畫。功能測試通過不代表已增加棋力；先保守設定，再依獨立對戰結果決定是否採用。

開局庫是選步流程的資料來源：先查庫、未命中再搜尋，不混入靜態 evaluator。王車易位歷史不在單一 FEN 中完整保存，優先用當前國王位置及安全特徵；本輪不新增歷史旗標。

## 搜尋擴充規劃

狀態：全部待做。先修正正確性，再量測效能；不為了較低節點數犧牲未說明的正確性。

| 子項 | 範圍 | 最小驗收 |
| --- | --- | --- |
| S0 終局與歷史 | 搜尋分支保留歷史、共用申請和棋政策、整理 Greedy 終局計分 | 重複局面與終局一致，搜尋結束／異常後根棋盤不變 |
| S1 Move ordering | 先做升變／吃子等基本排序；有基礎資料後再加入 PV、TT 或 history 排序 | 同深度完整搜尋最佳分數一致，同分走法可不同；報告節點與時間，無需每盤都更快 |
| S2 Quiescence | 深度邊界延伸必要交換；被將軍時搜尋合法應將 | 防止交換中途誤判，不能被將軍時直接 stand pat；定義停止邊界 |
| S3 迭代加深與時間 | 逐深度完成，實作 time_ms／停止訊號及可用結果回傳 | 回傳最後完成輪次，區分完成深度與探索深度，逾時／取消不破壞棋盤 |
| S4 置換表 | 保存深度、最佳走法、分數與 EXACT／LOWER／UPPER 界限 | key／和棋歷史、將死分數距離、不同設定的隔離與快取失效正確 |
| S5 進階搜尋 | PVS／aspiration，再評估 LMR／Null move，分別立任務 | 重搜邊界及戰術回歸測試；選擇性剪枝不可沿用完整 Minimax 等價假設 |

S0 優先；S1/S2/S3 各自驗收後再進 S4/S5。S4 完成後可回頭擴充 S1 的 TT move。時間控制在 S3 才實作，前面不得宣稱 time_ms 已生效。

本計畫不一次重寫所有搜尋。基礎功能完成後若需要 UI／CLI 的 Alpha-Beta 選項，再安排整合任務，保持相同設定在選步與紀錄中的一致性。
