# Alpha-Beta 多核心搜尋與有界置換表

## 問題陳述

固定深度 5 的 Alpha-Beta 單步搜尋等待過久。目前自動對戰的程序並行分派不同對局，不能加速同一局面的搜尋。置換表只有同鍵覆寫的取捨，缺乏容量上限與全表淘汰；每次搜尋結束即丟棄內容。

使用者希望所有 Alpha-Beta 使用情境能設定搜尋 worker 數，自動對戰也能讓每盤搜尋多核心執行，同時保留可設定的同時對局數與逐場保存。

## 解決方案

提供能實際跨核心執行的 Alpha-Beta 搜尋，將搜尋 worker 數與同時對局數分開設定，不新增依 CPU 核心數限制兩者乘積的規則。以程序平行根節點分枝作為優先評估方案，涵蓋真人對 AI、一般批次 Alpha-Beta 對戰，以及評分比較的 UI、CLI 和服務介面。

置換表先加入最大項目數及淘汰策略，以搜尋深度、界限類型與世代新舊衡量保留價值。初版仍限同一次搜尋使用；跨搜尋保留只做後續可行性評估，不直接上線。

## 使用者故事

1. 身為真人對 AI 的使用者，我希望單次 Alpha-Beta 搜尋能使用多核心，以縮短固定深度 5 的落子等待。
2. 身為使用者，我希望設定每次搜尋的 worker 數，以選擇投入多少 CPU 工作資源。
3. 身為服務介面使用者，我希望同一搜尋能力能用於各 Alpha-Beta 呼叫入口，以維持設定語意一致。
4. 身為使用者，我希望 worker 代表可執行 CPU 工作的單位，以取得多核心效果，而不被純 Python threads 的限制影響。
5. 身為自動對戰使用者，我希望一般批次能選 Alpha-Beta 對戰，以直接產生所需對局。
6. 身為自動對戰使用者，我希望同時對局數與搜尋 worker 數分開設定，以調整每盤速度與批次吞吐。
7. 身為自動對戰使用者，我希望這兩個設定的乘積可超過核心數，以自行決定資源配置。
8. 身為自動對戰使用者，我希望每場完成即保存，以在整批完成前取得可回放結果。
9. 身為使用者，我希望停止或離開時取消在途搜尋並清理程序，以結束工作而不遺留背景計算。
10. 身為使用者，我希望搜尋逾時或取消時取得既有契約允許的結果，以避免半完成分枝被當成完整搜尋。
11. 身為使用者，我希望 worker 故障能回報失敗且保留已發布對局，以理解問題並取得既有成果。
12. 身為使用者，我希望置換表項目數有上限，以限制每張表的成長。
13. 身為使用者，我希望容量滿時優先保留較有價值的結果，以減少丟棄深度、精確界限與新近資訊的代價。
14. 身為使用者，我希望不同棋規歷史、將死距離或評分設定的結果不被混用，以維持搜尋語意。
15. 身為評分比較使用者，我希望基準設定和各候選設定使用相同搜尋 worker 與置換表條件，以保持比較條件一致。
16. 身為對局紀錄使用者，我希望保存實際使用的搜尋與置換表設定，以理解對戰條件。
17. 身為對局紀錄使用者，我希望既有批次與棋譜仍能讀取，以持續使用已保存資料。
18. 身為使用者，我希望多核心結果符合合法落子與搜尋契約，而不要求與單 worker 的選步、平手順序及統計逐項相同。
19. 身為開發者，我希望以固定局面與深度 5 比較耗時、節點量與程序樹記憶體，以判斷方案是否改善等待。
20. 身為開發者，我希望分開量測啟動成本和後續多步成本，以避免只看單次速度而忽略程序池開銷。
21. 身為開發者，我希望評估跨搜尋保留的命中效益與安全條件，以決定是否值得另行實作。

## 實作決策

- 所有現有 Alpha-Beta 使用入口共用搜尋能力；一般批次補上 Alpha-Beta 選項。既有未使用 Alpha-Beta 的資料生成器與對戰 CLI 不因此全面擴充。
- 搜尋 worker 數是正整數，代表單次搜尋的 CPU 計算並行上限；worker 可是程序，不要求使用作業系統 threads。worker 數 1 保留為相容入口與效能基準，多場並行不能成為強制搜尋降為 1 的理由。
- 同時對局數沿用既有設定語意；不新增按「同時對局數 × 搜尋 worker 數」限制 CPU 的規則。可派分枝數、可派對局數與程序池平台限制仍須如實處理。
- 優先評估根節點分枝的程序平行化，沿用迭代加深、既有搜尋選項與評分器。最終分枝策略、程序池重用生命週期及置換表共享方式，需用實測選定並記錄，避免把程序建立成本放大到每個搜尋節點。
- 分派時保留完整走法歷史與相對於原根節點的深度；協調端和 worker 不共用可修改的正式棋盤。不以單一 FEN 取代棋規歷史。
- 程序間傳遞可還原的評分設定與搜尋條件；取消回呼由協調端轉成可傳遞的控制訊號。評分器無法供多程序使用時須明確回報，不可靜默更換評分器。
- 只把整個已完成的迭代當作完成深度；逾時或合作式取消延續既有回傳契約。內部節點數、走法順序和單 worker 結果不要求逐項一致，將死、和棋、評分視角與深度語意仍須正確。
- 置換表容量以最大項目數定義，必須有有限的預設值並可透過搜尋設定調整。淘汰考量深度、EXACT／LOWER／UPPER 界限類型及世代新舊；公式與預設值由基準實驗選定。處理同鍵更新與不同鍵間的容量淘汰，不能只在滿額時清空整張表。
- 同次搜尋的迭代可重用置換資料，下一次搜尋仍建立新內容。若 worker 各持私有表，每張表均須有界，且需明確記錄容量單位、表份數與總記憶體；單表項目上限不等於整個程序樹的位元組上限。
- 搜尋 worker 與置換表條件納入實際玩家設定快照，基準設定與候選設定使用相同搜尋條件。必要時調整版本，舊資料缺少新欄位仍可讀取，不虛構舊對局使用過多核心。
- 真人對局保留舊結果不得套入新對局的隔離；一般批次保留暫停／繼續的落子邊界語意，評分比較維持不提供暫停；停止、錯誤和保存失敗須清理內外層程序並保留可讀的已發布結果。
- worker 預設值及有限置換表預設容量需在實作時根據量測選定並記錄。本規格不預先指定加速倍數或容量數字。
- 不需獨立的大範圍重構票；必要的搜尋協調與設定傳遞調整納入各功能切片，沿用現有搜尋與對局介面。

## 測試決策

主要測試介面是公開的 AlphaBetaSearcher.search：從有歷史的棋盤與搜尋條件輸入，驗證合法選步、戰術或終局語意、完成深度、取消／逾時結果及輸入棋盤不被修改。沿用既有搜尋、迭代加深與置換表測試的案例；不要求平行結果與單 worker 逐項相同，也不能只驗證有回傳任一合法走法。

必要的上層整合介面是既有即時對局與批次服務的開始、停止及紀錄讀取流程。沿用背景選步、Alpha-Beta 評分比較、平行批次及 UI 事件測試，驗證 UI／CLI 設定實際影響搜尋、逐場發布、共同搜尋條件與舊紀錄相容。這些流程也驗證一般批次新增的 Alpha-Beta 對戰。

容量與替換直接透過置換表公開存取行為驗證：持續寫入仍有界，保留偏好可觀察，淘汰後搜尋可繼續；避免鎖定私有容器、IPC 訊息格式或特定內部方法。

至少有有界的真實 Windows spawn 整合案例，涵蓋外層多場與內層多搜尋 worker、合作式停止、worker 故障及清理。以小局面或有限手數完成，不在例行測試跑長時間深度 5 對局。超額派工行為可用有限工作量驗證不被新增的 CPU 乘積規則縮減。

效能以獨立基準量測，記錄局面、評分設定、搜尋選項、硬體邏輯處理器數、作業系統及 Python 版本；比較單 worker 與多 worker 的深度 5 耗時、節點量、整個程序樹峰值記憶體與冷／熱啟動成本。固定總工作量衡量批次吞吐，並記錄超額派工下的結果。不用脆弱的 CI 秒數斷言代替效能證據。

只新增能驗證上述重要行為或避免回歸的測試，不測靜態文案、匯出存在或 SDK 呼叫是否出現。

## 範圍外

- 正式跨步、跨對局、跨評分設定保留或共享置換內容；本次只包括後續可行性評估。
- 強制要求單 worker 與多 worker 的最佳走法、平手選擇、分數或節點統計逐項一致。
- 依 CPU 核心數限制兩層 worker 數的乘積，或自動改成搜尋單 worker。
- 新增評分項、歷史啟發式、LMR、Null-move、自動調參及其他棋力演算法。
- 以固定時間取代既有固定深度評分比較，或新增跨機器分散式計算。
- 為現有未使用 Alpha-Beta 的資料生成器與對戰 CLI 全面新增策略。

## 補充

使用者已確認多核心目標、所有 Alpha-Beta 使用情境、兩個並行設定並存且不加乘積限制、有界置換表方向及跨搜尋保留延後評估。跨搜尋可行性需特別分析根節點距離與將死分數、可逆歷史、和棋政策、評分設定失效及命中效益。

跨搜尋評估應交付可驗證的結論與建議；若值得實作，另行建立正式持久化規格，不能在評估票中直接啟用。
